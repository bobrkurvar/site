**Коммерческий веб-каталог отделочной плитки**

## О проекте

Keramovibor - коммерческий веб-каталог отделочной плитки, разработанный с нуля и используемый заказчиком.

Сайт помогает пользователям выбирать материалы двумя способами: искать отдельные позиции по техническим характеристикам или просматривать готовые дизайнерские коллекции. Административная панель позволяет сотрудникам самостоятельно поддерживать ассортимент, изображения и рекламные материалы в актуальном состоянии.

Публичная часть построена на серверном рендеринге. Основное приложение реализовано на FastAPI, данные каталога хранятся в PostgreSQL, Redis используется для кэширования и временных данных, а обработка изображений вынесена в отдельный сервис.

## Ключевые сценарии

### Выбор плитки

**Подбор по характеристикам.** Пользователь переходит в нужную категорию и фильтрует ассортимент по производителю, цвету, размеру, поверхности и другим параметрам.

**Просмотр коллекций.** Помимо отдельных товаров, каталог поддерживает интерьерные коллекции. Пользователь может сначала выбрать стиль или готовое визуальное решение, а затем перейти к товарам выбранной серии.

**Карточка товара.** Детальная страница содержит характеристики товара, данные об упаковке, изображения и информацию, необходимую для выбора материала.

**Пагинация.** Каталоги товаров и коллекций разбиты на страницы, чтобы не загружать весь ассортимент одним запросом.

### Управление ассортиментом

**Административная панель.** Менеджеры могут добавлять и редактировать товары, коллекции, категории, характеристики, изображения и баннеры без участия разработчика.

**Работа со справочниками.** При создании товара система использует существующие или создаёт недостающие связанные сущности: категорию, производителя, размер, цвет, поверхность, данные об упаковке и другие параметры.

**Развитие рабочего каталога.** Приложение и схема базы данных дорабатывались уже в процессе работы сайта. Изменения в моделях и функциональности вносились с сохранением ранее добавленных товаров и связанных сущностей.

### Изображения

**Хранение медиа.** Изображения хранятся в файловой системе, а в PostgreSQL сохраняются пути к файлам и связи с товарами или коллекциями.

**Миниатюры.** При загрузке изображений создаются отдельные версии для каталога, карточек товаров, коллекций и слайдеров. Это снижает объём передаваемых данных и ускоряет загрузку страниц.

**Защита от дубликатов.** Имена файлов формируются на основе хеша содержимого изображения, поэтому одинаковые файлы не сохраняются повторно.

**Отдельный image service.** Изменение размера и обработка изображений выполняются вне основного приложения, чтобы ресурсоёмкие операции не замедляли работу публичного сайта и административной панели.

### Авторизация администратора

Доступ к административной панели защищён авторизацией на основе JWT access и refresh token.

Токены передаются в `HttpOnly` cookie с настройками `SameSite=Strict` и `Secure` для production-окружения. Это ограничивает доступ JavaScript к токенам и снижает риски, связанные с XSS и межсайтовыми запросами.

## Устройство приложения

```text
Браузер
   │
   ▼
Traefik
   │
   ▼
Nginx
   │
   ▼
FastAPI application
   ├── PostgreSQL
   ├── Redis
   └── Image service
```

**FastAPI application.** Обрабатывает публичные и административные запросы, формирует SSR-страницы, управляет каталогом, авторизацией и связанными данными.

**PostgreSQL.** Хранит товары, категории, коллекции, характеристики, изображения, административные учётные записи и связи между сущностями.

**Redis.** Используется для кэширования и хранения временных служебных данных.

**Image service.** Генерирует миниатюры изображений с помощью Pillow. Тяжёлые операции обработки выполняются в отдельных процессах, чтобы не блокировать event loop основного приложения.

### Организация backend-кода

* `api/` - маршрутизация, HTTP-слой, SSR-страницы, обработка запросов и проверка доступа.
* `services/` - прикладные сценарии управления товарами, коллекциями, категориями и контентом.
* `domain/` - доменные сущности и бизнес-правила каталога.
* `adapters/` - работа с PostgreSQL, Redis, файловой системой и внешним image service.
* `infra/` - авторизация, безопасность, транзакции и технические сервисы.
* `db/` - SQLAlchemy-модели, мапперы и слой доступа к данным.

Прикладные сервисы работают с доменными объектами, а детали SQLAlchemy, файловой системы и HTTP-взаимодействия изолированы в инфраструктурных адаптерах. Операции, затрагивающие несколько связанных сущностей, выполняются в рамках Unit of Work и одной транзакции.

## Производительность и надёжность

* Публичные страницы формируются на сервере через Jinja2, что уменьшает объём клиентской логики и позволяет сразу отдавать готовый HTML.

* Для страниц каталога используется пагинация, а поля, участвующие в фильтрации и поиске, индексируются на уровне базы данных.

* Подключения к PostgreSQL, Redis и внешнему image service создаются при запуске приложения и переиспользуются в течение его работы.

* При ошибке во время сохранения медиафайлов файловая сессия выполняет компенсирующее удаление уже созданных файлов.

## Тестирование

Проект покрыт несколькими уровнями автоматизированных тестов:

* **Unit-тесты** - проверка доменной логики, вспомогательных функций и отдельных компонентов.

* **Integration-тесты** - проверка взаимодействия сервисов с PostgreSQL, файловым хранилищем и инфраструктурными адаптерами.

* **E2E-тесты** - проверка пользовательских сценариев публичной части и административной панели.

## Запуск

Для запуска проекта необходимы Docker Engine, Docker Compose и файл `.env` с параметрами окружения.

```bash
git clone <repository-url>
cd keramovibor
docker compose up --build
```

После запуска приложение, база данных, Redis, Nginx и связанные сервисы поднимаются в контейнерном окружении.
